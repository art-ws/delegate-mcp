# MCP-инструмент `decision` в `delegate-mcp` — спецификация v0.2

Дата: 2026-10-03. Статус: **DRAFT / REVIEW**, готов к архитектурному рассмотрению и постановке реализации. Документ задаёт расширение существующего `delegate-mcp`; реализация и выпуск ещё не выполнены. Канон спецификации и схем находится в этом репозитории, `docs/decision/`.

## 1. Цель и интеграция в существующий сервер

Добавить в `delegate-mcp` универсальный инструмент `decision`: передать контекст, вопросы и допустимые ответы в Jev через OpenRouter, получить проверенные типизированные ответы и вероятности. Применения: классификация, маршрутизация, проверка условий, оценка по шкале, сравнение кандидатов. Универсальность означает произвольную предметную область внутри поддерживаемых Jev типов вопросов.

**Размещение зафиксировано:** тот же npm-пакет `delegate-mcp`, тот же бинарник `delegate-mcp`, stdio MCP-сервер и конфигурационный файл. Отдельный сервер, пакет, процесс, MCP-регистрация и новая переменная пути к конфигу не создаются. Рантайм сохраняется **Node.js ≥20**, TypeScript и существующие MCP SDK / Zod из lockfile. Запрос Jev выполняется HTTPS `fetch`, отдельно от генеративного OpenAI-compatible пула; дополнительный SDK OpenAI/TypeSafe не нужен.

Исходная база интеграции: commit `105cc6d017f7de7f6afd012b53b590b487436aad`, package version 1.0.0. Проверено чтением [package.json](../../package.json), [config.ts](../../src/config.ts), [tools.ts](../../src/tools.ts), [metrics.ts](../../src/metrics.ts) и [index.ts](../../src/index.ts): сервер регистрирует `analyze/query/resume`, конфиг требует непустой активный `providers[]`, пул использует генеративный протокол, а query/resume хранят локальные сессии.

### 1.1 Регистрация и границы модулей

- `src/config.ts`: добавить опциональный верхнеуровневый блок `decision` в `AppConfig` и его загрузку по §8. Существующие поля и порядок резолва пути сохраняются.
- `src/tools.ts`: расширить `ToolContext` отдельным контекстом decision; `createServer()` регистрирует прежние три инструмента и `registerDecisionTool()`. `registerDelegateTools()` сохраняет нынешние контракты.
- Новые модули, предлагаемая раскладка: `src/decision/{config,schemas,client,assessment,tool,metrics}.ts`. `client` вызывает Decisions API; `tool` возвращает MCP-результат; `assessment` применяет локальные пороги. Транспорт, часы и генератор request_id внедряются для локальных тестов.
- `src/index.ts`: существующий единственный вход и stdio transport. Lifecycle/отмена новых запросов принадлежат тому же процессу сервера.
- `src/providers.ts`, `src/files.ts`, `src/sessions.ts`: `decision` их не вызывает. Контекст берётся только из аргументов; reader prompt, file walker, weighted pool, default_max_output_tokens и сохранённые delegate-сессии не применяются к Jev.
- `src/metrics.ts`: прежний формат JSONL сохраняется; новые метрики по §8 пишутся отдельно. `decision.session_id` — upstream correlation ID, не ID для `resume`.
- Схемы `docs/decision/*.schema.json` — канон аргументов и результатов. Runtime-валидатор/схемы tools/list должны соответствовать им; паритет входит в приёмку. Runtime-ресурсы должны попасть в существующий `dist` bundle, не требуя чтения checkout `docs/` после установки npm-пакета.

### 1.2 Совместимость и обнаружение инструмента

После реализации при обычном старте `tools/list` содержит **четыре** инструмента: `analyze`, `query`, `resume`, `decision`. Если блок `decision` отсутствует в старом конфиге, прежние инструменты продолжают работать, OpenRouter API key не требуется; `decision` обнаруживается, но его вызов возвращает `CONFIG_ERROR` с инструкцией добавить конфигурационный блок. Неявно читать OPENROUTER_API_KEY и активировать интеграцию при отсутствии блока нельзя.

`decision.enabled=false` явно убирает только новый инструмент из tools/list; его ключ и остальные настройки не резолвятся, сервер предоставляет прежние три инструмента. При включённом блоке (`enabled` отсутствует или true) битая конфигурация/отсутствующий ключ — fail-loud на старте, без скрытого отключения. Инвентарь фиксируется при запуске, hot reload не добавляется.

Для `analyze/query/resume` сохраняются аргументы, ответы с прежним заголовком, хранение сессий, пул, метрики и ошибки. Конфиг с одним decision и без providers[] не становится допустимым: изменение обязательности существующего пула — отдельная задача. Подключённым MCP-клиентам достаточно обновить установленную версию `delegate-mcp` и дополнить существующий config; отдельная запись `mcpServers.decision` не нужна.

## 2. Проверенный внешний контракт

На дату чтения `~typesafe/jev-latest` указывает на Jev 1.13; endpoint — `POST https://openrouter.ai/api/alpha/decisions`, аутентификация — OpenRouter Bearer API key. Jev принимает структурированный контекст и возвращает решения, без свободного текста и объяснения. [Страница модели](https://openrouter.ai/~typesafe/jev-latest), [руководство Jev](https://openrouter.ai/docs/guides/community/jev).

Документация открылась без входа. Через изолированный Playwright прочитаны страница модели, Decisions API и SDK guide; источник дочерних схем — опубликованный OpenAPI. URL, способ чтения и отпечаток источника — [sources.json](sources.json). Живой запрос с оплатой **NOT_RUN**; примеры ниже синтетические.

Для v0.2 выбирается Decisions API. Альтернатива TypeSafe SDK — `POST /api/v1/systemone` с base URL `https://openrouter.ai/api`; автоматически переключаться между этими поверхностями нельзя. [SDK guide](https://openrouter.ai/docs/guides/community/typesafe-sdk).

Контекст модели заявлен как 32 000 токенов, цена на момент чтения — $0.042 за миллион входных токенов, выход бесплатный. Это снимок, не постоянный тариф и не SLA. Стоимость вызова берём из `usage.cost`, если поле присутствует. [Карточка модели](https://openrouter.ai/~typesafe/jev-latest).

## 3. MCP-контракт и полный вход

Имя инструмента — `decision`. Описание должно прямо сообщать: отправляет предоставленный контекст во внешний API, возвращает Choice/Noul/Score, не выполняет выбранное действие и не генерирует объяснений. `tools/list` объявляет `inputSchema` и `outputSchema`; `execution.taskSupport="forbidden"`. Аннотации: `readOnlyHint=true`, `destructiveHint=false`, `idempotentHint=false`, `openWorldHint=true`: бизнес-данные не меняются, но запрос оплачивается, а повтор не гарантирует те же вероятности.

Канон полей и типов — [input.schema.json](input.schema.json), [output.schema.json](output.schema.json). JSON Schema 2020-12. Исходные определения адаптированы из OpenRouter OpenAPI с заявленной лицензией MIT; атрибуция — `sources.json`. Дополнительные семантические проверки перечислены ниже. Структурированный результат дублируется сериализованным JSON в одном текстовом блоке для совместимости клиентов. [Спецификация MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

| Поле | Обязательное | Контракт |
|---|---|---|
| `state` | Да | Контекст: строка, JSON-объект или массив. Вложенные значения — любые JSON-значения. |
| `questions` | Да | Непустая карта `question_id → Question`; один или несколько вопросов. |
| `model` | Нет | Полный OpenRouter ID; по умолчанию из конфигурации, заводское значение `~typesafe/jev-latest`. |
| `provider` | Нет | Полный объект маршрутизации OpenRouter либо `null`; поля перечислены в §5. |
| `session_id` | Нет | Строка ≤256 символов для наблюдаемости; не создаёт историю контекста. |
| `trace` | Нет | Объект: `trace_id`, `trace_name`, `span_name`, `generation_name`, `parent_span_id` — строки; также произвольные JSON-метаданные. |
| `user` | Нет | Строка ≤256 символов; использовать обезличенный идентификатор. |
| `policy` | Нет | Локальная карта правил уверенности по ID вопроса (§6); во внешний API не отправляется. |
| `execution` | Нет | Локальные `timeout_ms`, `max_retries`, `dry_run`; во внешний API не отправляются. |

Первые семь полей соответствуют текущему [Decisions API / OpenAPI](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request). В инструменте `model` становится необязательным благодаря конфигурации сервера. Имена `state`, `questions`, `criteria` сохраняются без второго параллельного формата `context/options`.

`execution.timeout_ms`: целое 1 000–120 000, заводское значение 30 000; общий дедлайн очереди, попыток и ожиданий. `max_retries`: целое 0–2, заводское значение 0. `dry_run`: boolean, заводское значение false; валидирует и возвращает точное тело запроса после применения настроек, без сетевого обращения и списания. Сервер может установить более строгие пределы, превышение возвращает ошибку.

Не поддерживаются chat-поля `messages`, `system`, `temperature`, `top_p`, `seed`, `max_tokens`, `stream`, `tools`, `response_format`, reasoning или произвольные заголовки из аргументов. Они не входят в DecisionsRequest. Неизвестные поля контрактных объектов отвергаются, а содержимое пользовательских JSON-объектов внутри контекста и инструкций сохраняется.

## 4. Все типы вопросов

Общее поле `instructions` обязательно: строка, объект или массив. В инструкции должна находиться вся формулировка вопроса: `question_id` служит корреляции, не заменяет инструкцию. Каждый вопрос имеет ровно один `type`.

| Тип | `criteria` | Ответ |
|---|---|---|
| `choice` | Обязательная карта из 1–255 вариантов. Ключ — идентификатор ответа; описание — строка, объект, массив или `null`. | `choice`: выбранный ключ; при наличии — `probabilities` по ключам и `confidence`. |
| `noul` | Необязательно. Если задано — объект с обоими ключами `true` и `false`; каждый содержит строку, объект или массив. | `noul`: число [0,1], вероятность «да». Отдельного `confidence` нет. |
| `score` | Обязательный массив из 1–10 описаний: строки, объекты или массивы. Порядок задаёт шкалу 0…N−1. | `score`: число [0,N−1]; при наличии — `probabilities`, `confidence`, `legend`. |

[Choice](https://docs.typesafe.ai/primitives/choice), [Noul](https://docs.typesafe.ai/primitives/noul), [Score](https://docs.typesafe.ai/primitives/score).

**Расхождение документации:** OpenRouter OpenAPI задаёт `score.criteria.minItems=1`, руководство TypeSafe рекомендует минимум два уровня и максимум десять. Для полноты поддерживаем 1–10; один уровень сопровождаем предупреждением `degenerate_scale`. Для Choice один вариант тоже разрешён, но сопровождается `single_option`. Максимумы 255/10 взяты из руководств TypeSafe; их фактическая поддержка через OpenRouter проверяется при реализации. [OpenAPI](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request), [Score](https://docs.typesafe.ai/primitives/score), [Choice](https://docs.typesafe.ai/primitives/choice).

Choice выбирает один вариант. Для нескольких независимых меток используют несколько Noul-вопросов. Ранжирование кандидатов строится клиентом по нескольким Score-вопросам с одинаковой шкалой. Сравнение между кандидатами требует передать всех кандидатов в `state`; отдельного встроенного `rank` или `multi_select` у этого контракта нет.

Вопросы одного запроса независимы и не видят ответы друг друга; зависимые решения требуют последовательных MCP-вызовов с новым `state`. `session_id` не передаёт предыдущий контекст модели. [Tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial).

Для неполного списка вариантов клиент явно добавляет `other`, `unknown` или `needs_review` с описанием. Сервер не добавляет варианты и не меняет инструкцию: неполная вилка с уверенным ответом всё равно остаётся неполной.

## 5. Все параметры `provider`

Ниже полный список 14 полей текущего `ProviderPreferences`. Их наличие в схеме маршрутизатора не означает, что каждое существенно для единственного доступного провайдера Jev. Неприменимые требования могут привести к отсутствию подходящего endpoint; сервер возвращает ошибку без ослабления требований. [Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection).

| Поле | Тип / допустимые значения |
|---|---|
| `allow_fallbacks` | boolean или null; переключение между провайдерами той же модели. |
| `require_parameters` | boolean или null; требовать поддержку переданных параметров. |
| `data_collection` | `allow`, `deny` или null. |
| `zdr` | boolean или null. |
| `enforce_distillable_text` | boolean или null. |
| `only`, `ignore`, `order` | Массивы строк slug провайдеров либо null; порядок `order` значим. |
| `sort` | `price`, `throughput`, `latency`, `exacto`; объект `{by?, partition?}` либо null. `by` — те же значения/null; `partition` — `model`, `none` или null. |
| `max_price` | Объект с необязательными строками `prompt`, `completion`, `request`, `image`, `audio`. Первые две — USD/миллион токенов; остальные — USD/запрос, изображение, аудиоединицу. |
| `preferred_max_latency` | Число секунд, `{p50?,p75?,p90?,p99?}` либо null; значения percentiles — числа/null. Предпочтение, не гарантированный таймаут. |
| `preferred_min_throughput` | Число токенов/с либо аналогичный объект percentiles, либо null. |
| `quantizations` | Массив `int4`, `int8`, `fp4`, `mxfp4`, `nvfp4`, `fp6`, `fp8`, `mxfp8`, `fp16`, `bf16`, `fp32`, `unknown` либо null. |
| `options` | Карта provider slug → объект специфических опций; включает `typesafe`. Полный снимок 146 ключей находится в схеме. Содержимое объекта сохраняется как JSON; его интерпретация принадлежит провайдеру. |

Источник типов — [OpenAPI DecisionsRequest](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request). Неизвестный slug в `options` отвергается локально: исходный API предупреждает, что неизвестные ключи молча отбрасываются. Список обновляется версионированным изменением схемы. Неизвестные строковые slug в `only/ignore/order` допускаются по OpenAPI. Вложенные опции провайдера не являются обещанием поддержки chat-параметров Jev.

`max_price` ограничивает тариф маршрутизации, не совокупные расходы процесса. Повторы могут оплачиваться отдельно. В v0.2 жёсткий денежный лимит задаётся на стороне OpenRouter отдельным ключом; локальный инструмент не заявляет точный предварительный расчёт токенов/стоимости.

## 6. Локальная оценка достаточности ответа

Без `policy` для каждого вопроса возвращается `unassessed`; это успешное получение ответа, без вывода о его пригодности. Правила задаются отдельно для конкретной задачи и версии модели, без универсального «безопасного» порога. Уверенность распределения не равна разрешению на действие. [Tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial).

`policy[question_id]` обязан ссылаться на существующий вопрос и содержать совпадающий `type`:

- Choice: минимум одно из `min_confidence`, `min_probability`, `min_margin`, все [0,1]. `min_probability` сравнивается с вероятностью выбранного ответа; margin — разница двух наибольших вероятностей. Все заданные условия объединяются AND, сравнение `>=`. Если нужного поля нет, результат `uncertain`, причина `missing_metric`. Один вариант не позволяет проверить margin; равенство максимальных вероятностей даёт `uncertain/tie` при любой заданной Choice-политике.
- Noul: оба `false_max` и `true_min`, причём `0 <= false_max < true_min <= 1`. При `p <= false_max` — `accepted`, boolean false; при `p >= true_min` — `accepted`, boolean true; между ними — `uncertain`, значение null. Без политики значение — исходная вероятность.
- Score: `min_confidence` [0,1]; `accepted` при достаточной уверенности, иначе `uncertain`. Значение остаётся исходным числом шкалы; инструмент не округляет его в категорию и не объявляет его разрешением/запретом.

Для Choice/Score `value` — исходный выбранный ключ/число даже при `uncertain`; клиент обязан проверить `status`. Если policy отсутствует, `reasons=[]`. Причины — стабильные коды, например `below_confidence`, `below_probability`, `below_margin`, `ambiguous_probability`, `missing_metric`, `tie`. Неопределённость — нормальный результат, `isError=false`.

## 7. Возвращаемые данные и валидация

Успех: `{kind:"decision", result:{model,answers,usage,id?,provider?}, assessments, meta}`. `result` сохраняет документированные поля upstream без переименования и округления. Фактически ответившая модель сохраняется отдельно от запрошенной: alias может разрешиться в датированный ID. Наличие `id`, `provider`, `usage.cost`, Choice/Score confidence/probabilities/legend не требуется текущим OpenAPI; отсутствующие поля нельзя подменять нулями. [OpenAPI](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request).

Семантическая проверка ответа обязательна:

1. Набор IDs совпадает с запросом, тип каждого ответа соответствует вопросу.
2. Числа конечны; Noul, confidence и вероятности в [0,1]; score в [0,N−1].
3. Choice ссылается на заданный вариант. Если есть probabilities — все и только запрошенные варианты; выбранный ключ имеет максимальную вероятность, ничьи допустимы.
4. Для Score probabilities содержат все индексы строками `"0"`…`"N−1"`; legend, если есть, совпадает с исходными описаниями.
5. Сумма probabilities отличается от 1 не более чем на 0.02: проектный допуск учитывает округление публичных примеров. Значения не перенормируются. Если одновременно есть score и probabilities, проверяется `abs(score − Σ i*p_i) <= 0.02*(N−1)+0.02`. Допуски должны быть подтверждены live-smoke, а не расширены для прохождения ошибочного ответа.
6. `usage.input_tokens/output_tokens` — неотрицательные целые; cost, если есть, конечный и неотрицательный. Неизвестные дополнительные upstream поля не выводятся и не ломают результат.

Ошибочный JSON, несоответствие типов/вариантов/числовых диапазонов → `UPSTREAM_PROTOCOL`, без частичного принятого решения. Если метрики уверенности отсутствуют, это совместимый ответ и предупреждение `missing_optional_metrics`; policy решает его статус по §6.

`meta`: локальный `request_id`, `requested_model`, `elapsed_ms` (монотонные часы), `attempts` (число начатых HTTP-попыток), `api_version="alpha-decisions"`, `warnings[]`. В `dry_run`: `{kind:"dry_run",request:<готовое тело>,meta}` и attempts=0. Возвращаемое тело не содержит ключа или заголовка Authorization.

Операционные ошибки: `{kind:"error",error:{code,message,http_status?,retryable,billing_uncertain},meta}`, `isError=true`. Схема output покрывает успех, dry-run и ошибку. Неизвестное имя tool / некорректная структура самого JSON-RPC — стандартная ошибка MCP. Если SDK отклоняет аргументы до handler, клиент может получить стандартный Invalid params; семантические ошибки handler возвращает `INVALID_ARGUMENT`.

## 8. Расширение конфигурации `delegate-mcp`, сеть и ограничения

В существующий JSON-конфиг добавляется верхнеуровневый блок `decision`. Следующий **фрагмент** объединяется с прежними `providers`, `session_dir`, `metrics_file`, `file_walker` и другими полями; сам по себе он не является полным конфигом сервера:

```json
{
  "decision": {
    "enabled": true,
    "api_key": "env:OPENROUTER_API_KEY",
    "default_model": "~typesafe/jev-latest",
    "allowed_models": ["~typesafe/jev-latest", "typesafe/jev-1.13"],
    "provider_defaults": {},
    "required_provider": {},
    "timeout_ms": 30000,
    "max_retries": 0,
    "max_request_bytes": 262144,
    "max_response_bytes": 1048576,
    "max_concurrency": 4,
    "max_queue": 16,
    "http_referer": "https://example.org",
    "app_title": "Delegate MCP"
  }
}
```

`decision.enabled` — boolean, default true при наличии блока. При включённом блоке `api_key` обязателен; остальные значения получают показанные заводские defaults, кроме необязательных `http_referer`, `app_title` и `metrics_file`. `default_model` — непустая строка, `allowed_models` — непустой список непустых строк, включающий default_model. `provider_defaults` валидируется по ProviderPreferences; `required_provider` — по правилам ниже. Таймаут — целое 1000–120000 ms, повторы — целое 0–2, пределы bytes/concurrency — положительные целые, max_queue — целое ≥0. Неизвестные поля включённого блока — ошибка. `http_referer` при задании — публичный HTTPS URL без credentials, `app_title` — непустая строка; CR/LF в заголовках запрещены. Опциональный `decision.metrics_file` — отдельный путь JSONL для decision (раскрыть `~`, относительный путь разрешить от process.cwd()); не должен совпадать с текущим delegate metrics_file (проверять нормализованный путь и существующий realpath). Все пределы — настройки обёртки, не лимиты Jev.

Модель override допускается только из `decision.allowed_models`. Для стабильной калибровки рекомендуется закрепить версию; использование alias — осознанный выбор. [Tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial).

Путь к единственному конфигу резолвится существующим `src/config.ts`: **`--config` / `-c` / `--config=<path>` → `DELEGATE_MCP_CONFIG` → `$XDG_CONFIG_HOME/delegate-mcp/config.json` (по умолчанию `~/.config/delegate-mcp/config.json`) → `~/.delegate-mcp/config.json` → `~/.delegate-mcp.json`**. Явный несуществующий/битый источник — ошибка; если ни одного файла нет, сервер не запускается. Defaults блока decision не заменяют обязательный config. Новая переменная DECISION_MCP_CONFIG не используется.

Секрет `decision.api_key` исключительно через `env:VAR`: literal запрещён; отсутствие/пустое значение при включённом блоке — fail-loud на старте без печати значения. Это правило нового блока не меняет прежнее поведение ключей providers[]. Сервер сохраняет existing config-loader semantics для прежних провайдеров. Сеть нового клиента фиксирована на OpenRouter Decisions endpoint; произвольный base_url/redirects запрещены. Настройки base_url/headers генеративного пула не наследуются. Тестовый HTTP-транспорт внедряется dependency injection, не через аргументы клиента.

`provider_defaults` задаёт значения по умолчанию; входное `provider` переопределяет отдельные верхние поля целиком, без скрытого слияния списков. null provider означает отсутствие переопределений. `required_provider` допускает только `data_collection:"deny"`, `zdr:true`, `allow_fallbacks:false`, `require_parameters:true`, `only:[slug,…]`: обязательная политика администратора. Отсутствующие/null ограничения заполняются обязательными; явное ослабление первых четырёх → `POLICY_CONFLICT`. Для only: входной список должен быть непустым подмножеством обязательного; иначе ошибка, если отсутствует — обязательный список. required_provider не может быть ослаблен клиентом. Privacy-режим не заявляется, пока администратор его не настроил и провайдер не удовлетворил требованиям.

`HTTP-Referer` и `X-Title` выставляются только из конфигурации, необязательны. `session_id` передаётся в body, без дублирующего заголовка. `state/questions/policy` не записываются в штатные логи. Метрики decision по умолчанию в stderr: request_id, модель, статус, время, attempts, usage; stdout содержит только MCP JSON-RPC общего сервера. При заданном decision.metrics_file — отдельный JSONL с полями ts, request_id, tool="decision", requested_model, actual_model?, status, elapsed_ms, attempts, usage?, error_code?. Нет записи этих строк в прежний metrics_file или delegate sessions; ошибка записи предупреждает в stderr, не ломает результат. Схема старых метрик не меняется. Полные тела ошибок провайдера и trace не логируются: они могут отражать входные данные. Ошибка возвращает безопасное фиксированное описание, статус и request_id.

Лимит входа проверяется по UTF-8 байтам окончательного JSON. Это не проверка 32k токенов; превышение контекста может вернуть upstream ошибку. Автообрезания контекста нет. Ответ читается с байтовым пределом; oversized response → `UPSTREAM_PROTOCOL`. HTTP-запросы используют общий deadline и AbortSignal; отмена клиента отменяет fetch и очередь. При переполнении очереди — локальная `UPSTREAM_UNAVAILABLE` с безопасным сообщением и attempts=0. Счётчики concurrency освобождаются при любом исходе.

Не существует автоматического fallback на генеративную модель. max_retries=0 предотвращает незаметные повторные списания. Если пользователь явно задал 1–2, повтор разрешён только для сетевых сбоев, 429, 500/502/503/524/529; exponential backoff 250ms·2^n + jitter 0–250ms, Retry-After учитывается, всё внутри общего deadline. Не повторяются 400/401/402/403/404/413, плохой ответ, отмена. После неопределённого результата отправки `billing_uncertain=true`; retries не обеспечивают exactly-once. Исчерпание общего deadline → `UPSTREAM_TIMEOUT`.

| Событие | Код |
|---|---|
| Ошибка конфига / параметров / размера | `CONFIG_ERROR` / `INVALID_ARGUMENT` / `INPUT_TOO_LARGE` |
| 400, 413 | `UPSTREAM_REQUEST`, `INPUT_TOO_LARGE` |
| 401, 402, 403, 404 | `UPSTREAM_AUTH`, `UPSTREAM_PAYMENT`, `UPSTREAM_FORBIDDEN`, `UPSTREAM_NOT_FOUND` |
| 429 | `UPSTREAM_RATE_LIMIT` |
| 500, 502, 503, 529 и прочие 5xx | `UPSTREAM_UNAVAILABLE` (неизвестный 5xx автоматически не повторяется) |
| 524 / локальный deadline | `UPSTREAM_TIMEOUT` |
| Обрыв сети / отмена | `NETWORK_ERROR` / `CANCELLED` |
| Ответ нарушает контракт | `UPSTREAM_PROTOCOL` |

Прочие HTTP 4xx → `UPSTREAM_REQUEST`; неожиданные non-2xx → `UPSTREAM_PROTOCOL`. retryable означает допустимость нового запроса с учётом причины, не обещание бесплатного повтора; при CANCELLED/INVALID_ARGUMENT/PROTOCOL — false. Для TIMEOUT retryable=true, но автоматический повтор после общего deadline невозможен.

Контекст передаётся внешнему сервису по явному вызову инструмента. Инструмент decision не собирает контекст из окружения, не читает ключницы, файлы или историю агента. Ответ Jev — данные для клиента; он не выдаёт полномочия на shell, публикацию, оплату или обход человеческого согласования.

## 9. Пример использования

Синтетический запрос — три независимых вопроса о ходе работ:

```json
{
  "state": {
    "task": "Выпустить функцию экспорта",
    "facts": ["Сборка успешна", "Проверки корректности выгрузки ещё не проведены"]
  },
  "questions": {
    "next_step": {
      "type": "choice",
      "instructions": "Выбери следующий шаг с учётом фактов и условий каждого варианта.",
      "criteria": {
        "verify": "Проверить выгрузку, если её корректность ещё не подтверждена.",
        "release": "Выпустить после успешной проверки выгрузки.",
        "other": "Ни один вариант не соответствует доступным фактам."
      }
    },
    "is_verified": {
      "type": "noul",
      "instructions": "Подтверждена ли корректность выгрузки?",
      "criteria": {"true": "Есть успешная проверка выгрузки.", "false": "Проверка отсутствует или не прошла."}
    },
    "readiness": {
      "type": "score",
      "instructions": "Оцени готовность функции к выпуску.",
      "criteria": ["Работа не собрана", "Собрана, нужна проверка", "Собрана и проверена"]
    }
  },
  "execution": {"dry_run": true}
}
```

Для получения ответа убрать dry_run или установить false. Например, policy для `is_verified` может иметь `{type:"noul",false_max:0.1,true_min:0.9}` — это иллюстрация синтаксиса, не откалиброванный рабочий порог. Ответ нельзя заранее обещать; пример показывает форму запроса, а не результат живого вызова.

## 10. Критерии приёмки реализации и порядок поставки

1. Один MCP-клиент соединяется с существующим бинарником delegate-mcp по stdio; tools/list показывает analyze/query/resume/decision с согласованными схемами. При decision.enabled=false — прежние три инструмента. Legacy config без блока не требует OpenRouter ключа, прежние вызовы проходят, decision возвращает CONFIG_ERROR; включённый блок с отсутствующим ключом вызывает fail-loud на старте. Один вызов с Choice/Noul/Score проходит полный mock HTTP round-trip; state, structured instructions, null Choice descriptions, provider, trace, user, session_id передаются без потери. execution/policy/ключ не попадают в тело.
2. Отдельно проверяются границы 1/255/256 Choice, 1/10/11 Score, Noul без criteria и с обоими критериями, отсутствующие обязательные поля, неизвестные поля, вложенные JSON и byte limits. У 1-level/1-option есть предупреждения. Все 14 provider-полей и известные options проходят контрактные fixtures.
3. Контроли ответа: чужой option, пропавший ID, неверный тип, отрицательный cost, вероятность вне диапазона, неверная сумма, неправильная legend/score, HTML вместо JSON → ошибка. Отсутствующие необязательные метрики/usage.cost проходят без выдуманных значений; policy с недостающей метрикой даёт uncertain.
4. Пороговые контроли проверяют точные равенства границ, AND, ничью, неверный тип policy, несуществующий ID и invalid noul interval. Ни uncertain, ни error не превращаются в разрешение на действие.
5. Повторы, HTTP errors, общий deadline, отмена, очередь и cleanup проверяются локально детерминированным HTTP fixture. По умолчанию POST ровно один. В dry_run их ноль. mandatory-provider policy нельзя ослабить null/override; отказ удовлетворить ZDR/deny не вызывает обходной маршрут.
6. Secret-safe контроль: canary ключа и контекста отсутствует в stdout вне ожидаемого MCP-ответа, stderr и ошибках; ключ отсутствует во всех ответах. Вызов decision не запускает file walker/session loader, не получает доступ к браузеру и не выдаёт исполняемых действий; существующий analyze по-прежнему читает явно заданный work_dir.
7. После локальных контролей — независимый QA и один минимальный живой smoke на синтетических данных с предоставленным ключом: фактическая model/provider/usage, все три primitive, alias и закреплённая версия, проверка обязательных privacy-условий при их включении. До smoke — **NOT_RUN**, публикация не выдаётся за проверку API. Доступ/ключ решается отдельным безопасным каналом; логин оператора требуется только если он создаёт ключ в кабинете.
8. Регрессия существующего набора тестов подтверждает работу analyze/query/resume: input schemas, формат ответа, resume pinning, sessions, file excludes и метрики. Добавляются контроли изоляции обоих HTTP-протоколов и конфигураций. Конфиг-резолв проходит CLI/ENV/home сценарии; disabled decision не требует ключа; битый enabled block не игнорируется. Node 20 остаётся минимальным рантаймом.
9. Установочный smoke из npm pack-артефакта использует один существующий bin/config/stdio server; новый инструмент не зависит от пути docs/ в checkout. Build/lint/typecheck/test и secretlint — прежние проектные команды; публикация релиза через существующий release workflow после отдельного поручения, без нового пакета.

Поставка после отдельного поручения: (1) согласовать v0.2 контракта; (2) добавить decision в существующий сервер, config loader и README/examples; (3) независимая QA нового инструмента и регрессии; (4) подготовить проверенный пакет delegate-mcp и пример дополнения существующего конфига; (5) обновление/подключение/публикация существующего пакета в явно заданном объёме. Коммерческая оценка внедрения: реальные input_tokens, usage.cost и время на выбранных сценариях, без обещания ускорения/качества только по карточке модели.

## 11. Границы этой спецификации

Документация и схемы проверены чтением источников; live-инференс, эмпирическая калибровка, latency/throughput, доступность нужного privacy-endpoint и совместимость конкретных MCP-клиентов **NOT_RUN**. Пределы bytes, concurrency, retries, допуски ответа и схема policy — проектные решения обёртки. Сквозные tests и QA будут частью реализации; подготовка спецификации не означает ACCEPT инструмента.
